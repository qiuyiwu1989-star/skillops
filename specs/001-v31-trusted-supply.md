# 001: SkillOps V3.1 · 可信技能供给 MVP

## 要什么

为造物云能力市场建立一条只面向「技能」的可信供给流水线：从白名单 GitHub 仓库发现 `SKILL.md`，进入候选池，经格式、来源、许可证、安全、SMS 静态质量和人工审核后，生成可供市场消费的技能卡；候选永远不自动公开。

同时保留 SkillOps 的内部管理定位：市场负责发现与获取，SkillOps 负责技能的身份、版本、考核、部署与持续复评。本版先完成可信供给最小闭环，不扩展到插件、方法、应用和数字员工。

## 核心假设

1. 公开生态中存在足够多的合格 `SKILL.md`，值得通过自动发现降低供给成本。
2. 格式、许可、安全、SMS 与人工审核的组合，能把「公开候选」转化为「可信供给」。
3. 市场消费标准化技能卡即可，不必复制外部技能内容形成第二真身。

## 用户与核心流程

- 市场运营：配置白名单来源，运行采集，查看候选，批准或拒绝。
- 技能作者：后续可认领来源技能；本版只保留来源身份，不做作者后台。
- 市场消费者：只看到已批准的市场技能卡及其证据，不看到候选池。

流程：`source → candidate → gate audit → SMS → review → listing → rescan`。

## 本版范围

- 新代码在 `trusted-supply/` 隔离生长，不修改冻结中的生产接口和线上页面。
- 支持本地目录和 GitHub 仓库快照两种采集输入；网络采集必须显式调用。
- 内容指纹与 `source + path + commit` 版本身份。
- 格式检查、许可证分类、静态安全检查、重复检测。
- SMS 结果接入点；无 LLM 配置时标记为 `pending`，不得伪造分数。
- 候选状态机：`discovered / screening / review / approved / rejected / quarantined / stale`。
- 人工审核命令与不可变审核事件。
- 仅 `approved` 候选可生成市场技能卡。
- 上游内容变化后旧审核失效，回到复评流程。
- 自动化测试覆盖硬门、状态机和上架边界。

## 不做什么

- 不抓取插件、方法、应用或数字员工。
- 不做全 GitHub 无差别爬虫。
- 不自动公开、收费或分成。
- 不绕过许可证复制或再分发完整第三方内容。
- 不把 Star、下载量或 SMS 单分当准入结论。
- 不建设作者认领、支付、社区排行和完整市场前端。
- 不修改或部署 `api-server/`、`xiaoneng/` 和线上服务。

## 信任门

候选必须依次满足：

1. 格式可解析，存在有效名称与描述；
2. 来源、commit 和内容指纹完整；
3. 许可证明确允许，或降级为只索引源链接；
4. 无阻断级安全问题；
5. SMS 达到配置门槛，或经人工明确豁免并留痕；
6. 人工批准。

安全与许可证是硬门，不能被综合分抵消。

## 验收清单

- [ ] `node --test trusted-supply/test/*.test.mjs` 全部通过。
- [ ] 可从至少 3 个 fixture 仓库发现不少于 10 个候选。
- [ ] 同内容不同来源可识别为重复但保留来源血缘。
- [ ] 缺失/不明确许可证的候选不会携带可再分发内容上架。
- [ ] 含危险命令、凭证外传或远程执行模式的 fixture 被隔离。
- [ ] 未审核候选无法生成 listing。
- [ ] 批准动作记录审核人、时间、理由和基于的内容指纹。
- [ ] 内容变化后原批准失效并标记 `stale` 或重新进入审核。
- [ ] listing 含来源、版本、许可证、安全、SMS/Eval 状态与验证范围。
- [ ] 不需要真实密钥即可在 fixture 上完成端到端演示。

## Go / No-go

- Go：白名单试运行中 ≥50 个有效候选，来源/去重准确率 ≥95%，高风险零误上架，≥10 个完成评估，≥3 个可批准为精选。
- No-go：无法稳定判断来源与许可，或安全硬门出现误放；此时不开放市场，只保留内部候选研究。
