# 九个 play · 八个 HR 模块

> 把每个 skill 当员工管。九个动作覆盖从招聘到退役的完整生命周期。
> 分数口径统一用 **SMS v2.0**（100 分制，每维 0-10，段位 S86/A76/B64/C50）→ [sms.md](sms.md)

| HR 模块 | 做什么 | play |
|---|---|---|
| M·01 招聘 | 新 skill 入库 | skill-card-gen · skill-forge |
| M·02 评估 | 10 维评级定段位 | skill-audit |
| M·03 管理 | 编目 + 依赖/组合关系 | skill-registry-scan · skill-graph |
| M·04 分发 | 上架 / 被 agent 调用 | 平台原生（registry + API，不在本包） |
| M·05 培训 | 把不够分的带上一档 | skill-coach |
| M·06 绩效 | 持续监控、退化预警 | skill-metrics |
| M·07 项目评估 | 按 agent/项目盘点能力组合 | agent-capability-map |
| M·08 退役 | 下线、合并、可逆归档 | skill-retire |

闭环：招聘 → 评估 → 管理 → 分发 → 培训 → 绩效 → 项目评估 → 退役 → 回到招聘。

---

## 1 · skill-card-gen（M·01 招聘）
**触发**：「造一个 XX 技能」「帮我把这个做成技能卡」

访谈式生成标准技能卡——**先问清楚再动笔**，不要用户说一句你就写一版。

问这五个问题（一次问完，允许用户跳答）：
1. 这个技能替谁、在什么场景下、解决什么反复出现的问题？
2. 用户会怎么开口叫它？（收集真实触发词，越口语越好）
3. 输入是什么、输出长什么样？（要具体到格式）
4. 有哪些**坑/边界**是新手会踩的？（隐性经验——SMS 结果质量维度的关键）
5. 什么情况下**不该**用它？（反例边界，决定可调用性得分）

产出技能卡：`name` / `description`（含触发词，写成一句话让 agent 能判断何时调用）/ 核心步骤 / 输出格式 / 边界。
交付后接 **skill-forge** 落成真实文件，或直接写 SKILL.md 并**出生即入册**（见规约 1）。

## 2 · skill-forge（M·01 招聘）
**触发**：「造技能」「把这套方法做成 skill」

六阶段锻造，**每阶段做完给一句话汇报，不要闷头做完一整个**：

1. **意图捕获** — 用户到底想固化什么判断？（不是"想要什么功能"）
2. **写 SKILL.md** — frontmatter（name/description/id）+ 主体。description 是路由规则，必须让 agent 只读它就知道何时调用。
3. **参考文件** — 大块内容拆进 `references/*.md`，主体保持精简（渐进式披露：主体讲怎么做，references 存细节）。
4. **质量检查** — 自查 SMS 十维，重点：可调用性（删掉正文只留 description，还能判断何时调用吗）、结果质量（有没有沉淀坑与判断，还是在复述常识）。
5. **测试** — 造 2-3 个真实场景跑一遍，看是否被正确触发、产出是否稳定。
6. **迭代** — 按测试结果改，然后 `register` 落户 + `scan` 入册。

## 3 · skill-audit（M·02 评估）
**触发**：「审计一下 XX」「这个技能几分」

```bash
node <本技能目录>/scripts/skillops.mjs score <技能名>
```
需要用户自己的 `LLM_*` 环境变量（写在 `~/.skillops/env`）。**评分花的是用户的额度，批量前先请示。**

汇报格式（别贴原始 JSON）：
```
<技能名>  78/100  A 段
最弱：可评估性 4/10 —— 没有成功标准，好坏无法判断
      可组合性 5/10 —— 输入输出契约不清晰
建议：补一节「验收标准」+ 显式声明输入/输出格式。要我跑 skill-coach 提分吗？
```
没配 LLM 时的降级方案：按 [sms.md](sms.md) 的十维判据**人工对照打分**，标注"人工估分，非引擎评分"。

## 4 · skill-registry-scan（M·03 管理）
**触发**：「扫描一下技能库」「我有哪些技能」「盘点」

```bash
node <本技能目录>/scripts/skillops.mjs scan     # 盘点 + 体检
node <本技能目录>/scripts/skillops.mjs ls       # 花名册
```
读懂三种信号并**分别处置**：
- **无户口**（○）= 没有 `id`。原创的建议批量落户；第三方的留着（规约 3）。
- **分身**（≡，同指纹多处）= 内容相同的拷贝 = 事实上的手工部署。不是错误，但要让主人知道"这几处将来要一起更新"。
- **分歧**（✗，同身份不同指纹）= **版本漂移，最该处理**。摆出差异请主人选哪份是真身（规约 4）。

## 5 · skill-graph（M·03 管理）
**触发**：「技能关系」「这几个技能怎么配合」

维护技能间的两类关系，写进各自 frontmatter：
```yaml
relations:
  composeWith: [ns/skill-a]     # 常一起用（组合）
  dependsOn:   [ns/skill-b]     # 必须先有它（依赖）
```
判断依据：读 SKILL.md 找**显式引用**（A 的正文让用户接着用 B）、**输入输出契约吻合**（A 的产出正是 B 的输入）、**同场景高频共现**。
用途：退役前查谁依赖它（见 play 9）；组合成工作流；能力地图的连线。

## 6 · agent-capability-map（M·07 项目评估）
**触发**：「团队能力盘点」「这个项目/agent 有哪些能力」「我们缺什么能力」

按 agent / 项目分组盘点技能组合，产出能力地图：
```
项目 <名>  ·  装备 N 个技能
├─ 覆盖的能力域：写作 3 · 分析 2 · 工程 5
├─ 平均段位：B（S:1 A:2 B:4 C:1 D:0）
├─ 空白区：没有任何"测试/质检"类技能
└─ 冗余：<技能 X> 与 <技能 Y> 职责重叠 70%，建议合并或明确分工
```
数据来源：`ls --vault <项目卷>` + 各技能的评级与关系。**结论要落到"缺什么、重什么"**，不要只罗列清单。

## 7 · skill-coach（M·05 培训）
**触发**：「帮 XX 提分到 A」「辅导一下这个技能」「怎么改更好用」

前置：必须先有一次评级（没有就先跑 play 3）。

```
Step 1  载入技能 + 最近评级（10 维分数 + 每维评语）
Step 2  诊断提分杠杆：按"距满分缺口"排序取前 3 维；区分两类问题
        · 内容缺失（缺触发词/输出格式/示例）→ 直接补
        · 设计缺陷（职责过宽/步骤含糊/不可复现）→ 需重构
Step 3  逐维对症下药：
        清晰度↓     → 重写 description，一句话讲清"何时用/产出什么"
        可调用性↓   → 补触发词表 + 反例边界
        可执行性↓   → 流程拆成带编号的确定步骤，消灭"凭感觉"空步
        输出稳定性↓ → 显式定义输出格式/模板/schema
        结果质量↓   → 加验收标准 + 好坏对照示例 + 沉淀坑(gotchas)
        可复用性↓   → 抽参数、去硬编码、去项目专属假设
        可组合性↓   → 声明输入/输出契约
        可评估性↓   → 补"怎么算做对了"的成功标准
        安全性↓     → 标注禁用动作/需确认动作/数据边界
Step 4  产出重写稿（完整 SKILL.md，关键改动标出来）
Step 5  复评：before→after 每维 Δ、总分 Δ、段位是否跨档；未达标回 Step 3，最多 3 轮
```
**边界**：只重写内容与结构，不擅自改业务意图——拿不准的取舍标 `⚠ 需你确认`。不刷分（塞无意义内容会反向拉低清晰度）。重写稿是**建议**，写回由主人决定。

## 8 · skill-metrics（M·06 绩效）
**触发**：「哪些技能在退化」「技能绩效」「最近用得怎么样」

```bash
node <本技能目录>/scripts/skillops.mjs report
```
红黄绿三档判读：
- 🟢 **健康**：近期有调用、分数稳定或上升
- 🟡 **关注**：久未更新（>90 天）且仍在被调用 · 分数下滑 · 分身多处未同步
- 🔴 **退化**：长期零调用 · 段位跌档 · 存在分歧未解决

**退化预警的处置链**：metrics 发现退化 → 有价值就 **coach 提分** → 提分无效且低价值 → **retire 下线**。
诚实边界：没装遥测 hook 时没有调用数据，此时只能用"分数趋势 + 久未更新"，**要明说数据来源不全**。

## 9 · skill-retire（M·08 退役）
**触发**：「哪些技能该下线」「这个还要吗」「清理技能库」

```
Step 1  候选识别：长期零调用 + 低段位 + 长期未更新，或职责被新技能覆盖
Step 2  查依赖（关键，别漏）：谁 dependsOn 它、谁 composeWith 它、
        哪些项目卷里有它的分身 —— 有依赖就先给迁移指引，不能直接下
Step 3  给迁移指引：用哪个技能替代、差异在哪、调用方要改什么
Step 4  可逆归档：frontmatter 标 status: retired（+ 一行 retired_reason）
        **绝不删除文件**（规约 5）—— 退役是可逆的，删除不可逆
Step 5  汇报：下线了谁、为什么、影响谁、怎么回滚
```
必须**主人拍板后**才执行。合并（两个技能职责重叠）也走这条流程：留一个、另一个标退役并指向留下的那个。
